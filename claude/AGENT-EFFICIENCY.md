# Agent 执行效率（全局，适用于所有项目）

> 由 drsg-harness-kit 的 `claude/AGENT-EFFICIENCY.md` 安装到 `~/.claude/`，全局 CLAUDE.md 用 `@AGENT-EFFICIENCY.md` 引入。**改动请改仓库里那份**，这里的副本会被 `setup.sh` 覆盖。
> 复盘用 `agent-efficiency-retro` skill。

## 工具调用：互相独立的放在同一轮里发

- 每回复一次就是一次模型请求，每次都要带上整段上下文，很贵。**下一步调用不依赖上一步的结果时，就在同一次回复里一起发起。**
- **应该一起发的**：开工前要读的几个文件；要查的几个符号（grep / snippet / context）；`git status` / `git log` / `git diff` 这类只读检查；改完后互不依赖的验证，例如前端和后端的测试。**写操作也一样**：同一文件里几处互不重叠的修改，在同一轮里发多个 Edit；测试文件和生产文件的改动一起发；格式化和测试串成一条命令（`gofmt -w <文件> && go test …`）。
- **必须分开的**：只有一种情况——下一步要看上一步的**输出**才能决定。例如看了报错才知道改哪里，改完要跑测试才知道对不对，commit 之后才能查 tree。几处 Edit 之间互相不看对方的结果，不算这种情况。
- **读文件一次读完**：不带 offset，除非文件超过 2000 行。Edit 成功就说明已经改上了，不要为了确认去重读（见下面「状态检查」一节）。
- **自检**：如果连续三次回复都只发了一个调用（只读一个文件，只改一处，或只跑一条命令），就停下来想想，接下来的几步能不能一次发出去。
- 由来（写操作这一段）：2026-10-06 sub2api 实施段，181 轮单发调用里有 45 轮是 Edit 接 Edit，18 轮是分段读或改完重读，12 轮是 gofmt 和测试分两次发；而同一个模型在计划阶段有 51% 的轮次是多调用并发。
- 由来：2026-10-05 sub2api 一个会话里，901 次回复只有 47 次一次发起了多个调用（约 5%）。当时上下文中位 375k，每轮中位 17 秒，光模型生成就花了 366 分钟。

## Bash 的工作目录：每条命令自带目录，不要依赖上一条的 cd

- 命令**成功**（退出码 0）时，里面的 `cd` 会保留到下一条命令；命令**失败**时，下一条命令会回到 `cd` 之前的目录。所以「上一条打过 `cd backend`」不代表现在就在 `backend` 里，红绿测试循环里尤其如此，因为测试本来就会先失败。
- 写法：Go 用 `go -C backend test …`，git 用 `git -C <目录> …`，其他命令写成 `(cd backend && …)`，或者直接用绝对路径。
- 遇到 `no such file or directory` 时，先 `pwd` 确认目录，不要接着猜 `../` 前缀。
- 由来：2026-10-05 sub2api 的 `cd backend && go test` 因为测试失败，`cd` 没有保留下来。之后模型三次按「已经在 `backend/` 里」的相对路径执行 `gofmt` 和 `go test`，又猜了一次 `../backend`，四次都报 `lstat …: no such file or directory`，另外还跑了两次 `pwd` 排查。前后白白多出 6 次模型请求，每次都带着几十万 token 的上下文。

## 磁盘空间：先诊断，再清理 Go 缓存

- 遇到磁盘空间或 inode 报满，先运行 `df -h` 看各文件系统的空间用量；inode 报满也可能是空间耗尽的连带表现，不要先假定是小文件过多。
- 需要紧急腾空间时，可清理 Go 构建缓存：先用 `go env GOCACHE` 确认缓存目录，再用 `go clean -cache` 清除。缓存会在后续构建时重新生成；这是临时恢复手段，不是根因修复。缓存以外的文件不要擅自删除。
- 在临时副本中重复运行 Go 测试时，优先复用已有副本；必须新建副本时，可用 `go test -trimpath -count=1` 避免绝对目录路径阻止构建缓存复用。`-count=1` 禁用测试结果缓存，`-trimpath` 仍允许复用构建缓存。
- 不要把 `-trimpath` 设为全局 `GOFLAGS`：它会改变 `runtime.Caller` 返回的路径，可能影响依赖该路径的代码。使用前先用 `git grep runtime.Caller` 检查仓库；优先只在相应的测试命令上显式使用，避免扩大影响范围。
- 报满时能用上面的办法自己腾出空间，就直接腾，腾完继续原任务，在回执里写一句清了多少；不要停下来等人。只有清完缓存仍不够，或者要删缓存以外的东西时，才停下来问用户。
- 由来：2026-10-06 某项目验收阶段报「inode 100%」后停下等人，实际是空间满（剩 92K），Go 构建缓存占了 24G，清掉后空间用量 53%、inode 用量 4%，不到 5 分钟恢复；同样的事 9 月底也发生过，一天写回 24G，所有会话写文件都报 ENOSPC。实测新副本跑 `go test`：不加 `-trimpath` 时缓存 +474MB、耗时 89 秒，加了只多 2MB、耗时 7 秒。

## 状态检查：只在边界做，不在每一步后做

- Edit / Write 成功就说明改上了，不要每改一处就跑一次 `git status` / `git diff` 去确认。
- 状态检查（`git status`、`git diff --stat`、`git diff --check`）只在这三个时候做：**开工时**（确认起点）、**一个阶段结束时**（对照计划看改动范围）、**提交前**。
- 已经读过、并且之后自己没改过的文件，不要重读。要看改后的样子，只读改动的那一段。
- 计划已经写明了改哪个函数、哪个字段时，直接按计划去改，不要再用代码图或 grep 从头摸底。只有计划没写到的地方才去查。
- 查待办用 `event_list`。不要用 cypher 把记忆平面整个拉出来（`MATCH (f:Fact) RETURN f …`）：结果会超限，存成文件后还得分段读。要找某条 Fact，就按 `external_key` 或关键词查那一条。
- 由来（上一条）：2026-10-06 sub2api 用 `MATCH (f:Fact) RETURN f LIMIT 100` 查待办，结果 12.5 万字符超限，存成文件后分 8 次读完，成了那一段被读次数最多的文件。
- 收到判定（summary 以「验收通过：」开头），`event_done` 就是确认收到，不要再回 notice。只有要返工（「验收不通过：」）或有异议时才另发。
- 由来（上一条）：2026-10-06 一天里，sub2api 和 drsg-harness-kit 对判定回了至少 6 条「已收到、确认接受」，每条都要发件方再关一次单。起因是 poller 唤醒提示那句「做完发回执」对所有 Event 一视同仁。
- 收到派活（handoff）直接开工，不要先回「已读」「已收到，准备先写计划」这类 notice。回给发件方的第一条，应该是回执，或者卡住时要问的问题。
- 由来（上一条）：2026-10-06 晚到 10-07，判定已经不回 notice 了，sub2api 仍回了 5 条这类确认（「已读修复方向」「已收到计划评审通过及 T1/T2 提示」等，另有一条核验回执发了两遍），每条都要发件方再关一次单。
- 由来：2026-10-05 sub2api 实现功能 1，954 行（约 600 行测试）用了约 1500 次工具调用，其中 `git status --short` 202 次、各种 `git diff` 140 多次、`AccountsView.vue` 被读了 59 次、代码图调用 463 次。正常规模应在一百次左右。

## 验证：同一棵 tree 不重验，整包测试只在交付前跑一次

- **tree 没变，就不重做验证。** 每次整包测试跑完，记下当时的 tree（`git add -A && git write-tree`），写进交接文件或回执草稿。用户要求 commit 时再算一次：
  - 和记下的一样：不再跑测试，直接提交，并引用那次的结果（命令、通过数、tree）；
  - 不一样：只对改动所在的包或模块跑定向测试，不重跑整包，也不重做变异自检。
- `verification-before-completion` 一类流程要的是「新鲜的证据」。在同一棵 tree 上跑出来的结果，就是新鲜证据。
- **开发过程中只跑定向用例，整包在交付前只跑一次。** 输出用机器可读的格式写进文件（如 `go test -json > 文件`、`pytest --junitxml=文件`），再用一条命令只取出失败项。不要把几 MB 的输出直接打进上下文。
- 有输出过滤代理（如 rtk）时，用它的直通方式（`rtk proxy …`）把原始输出写进文件。过滤器截断之后，只能读它的日志副本重新解析，或者再跑一遍。
- **已知的老红要事先点名**（写进计划或交接文件）。失败项只有这几条，就等于通过；多出来的，先到父提交上单跑那一条，分清是新红还是老红，不要重跑整包。
- 由来：2026-10-05 sub2api 功能 2，用户说「创建这个 commit」之后又过了 53 分钟才提交。这期间整包测试（一次约 3.6 分钟）又跑了 3 次，变异自检手工重做了一遍，最后是用户叫停。而这棵树在之前已经全量验证过两次。整个功能 2 段整包测试一共跑了 7 次，约 25 分钟。每次输出都超过 10 MiB，被 rtk 截断，每次都因为 3 条已知的老红返回退出码 1。

## 上下文：过了 300k 每轮明显变慢，阶段边界要交接

- **缓存只省钱，不省时间**：生成每个 token 都要对整段上下文做注意力计算。实测（缓存命中 >90%、输出 <200 token）：300k 以内约 7–9 秒一轮，300–400k 约 13 秒，500k 以上约 21 秒。
- 用 1M 窗口的模型时，在项目的 `.claude/settings.local.json` 的 `env` 里设 `"CLAUDE_CODE_AUTO_COMPACT_WINDOW": "300000"`。默认要接近 1M 才会自动压缩。**必须写纯数字**：环境变量按 `parseInt` 解析，`"300k"` 会被读成 300，再被下限抬到 100k，结果每到约 67k 就压缩一次（2026-10-05 sub2api 实测）。`k` 简写只在 `/config` 里有效。
- `/compact` 和 `/clear` agent 自己发不出来。到了阶段边界（计划评审通过 / 交回执 / 开始下一个功能），**先写交接文件，再提醒用户 `/clear`**。
- 交接文件写五项：计划路径、起点 tree、做到第几步、下一步、**用户中途口头给的指令**（原话照抄，并注明是长期有效还是只这一次）。压缩后，最容易丢的就是这类只存在于对话里的指令。

## 交付闭环与防遗漏：不把用户当 linter

- 准备交回（发回执或请求 commit）之前，运行 `completeness-guard.py`，并将输出原文贴进回执的「用户入口」一节。
- 守卫报出的「新名字没有文档」，必须补齐文档，或在回执中逐条说明免除原因。
- 不要等用户审核提醒才补齐文档；测试通过不等于交付完毕。
