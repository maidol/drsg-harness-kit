# Agent 执行效率（全局，适用于所有项目）

> 由 drsg-harness-kit 的 `claude/AGENT-EFFICIENCY.md` 安装到 `~/.claude/`，全局 CLAUDE.md 用 `@AGENT-EFFICIENCY.md` 引入。**改动请改仓库里那份**，这里的副本会被 `setup.sh` 覆盖。复盘用 `agent-efficiency-retro` skill。

## 工具调用：互相独立的放在同一轮里发

- 每次回复都带整段上下文，很贵。**下一步不依赖上一步的输出，就在同一次回复里一起发**：开工要读的几个文件、要查的几个符号、`git status`/`log`/`diff` 这类只读检查、互不依赖的验证。
- 写操作也一样：同一文件里相隔较远、互不重叠的几处，同一轮发多个 Edit；挨得近的几处合成一个覆盖整段的 Edit，不要拆开发；测试和生产文件的改动一起发；格式化和测试串成一条命令。`&&` 只用在后一条依赖前一条成功时；互相独立、可能失败的检查拆开发或用 `;` 连。
- 只有「要看上一步的输出才能决定下一步」才分开发。文件一次读完（超过 2000 行才用 offset）。连续三次回复都只发一个调用，就停下想想能不能合并。

## Bash 的工作目录

命令失败时下一条会回到 `cd` 之前的目录。每条命令自带目录：`go -C dir`、`git -C dir`、`(cd dir && …)` 或绝对路径。报 `no such file or directory` 先 `pwd`。

## 磁盘空间

报满先 `df -h`。可以自己清 Go 构建缓存（`go env GOCACHE` 确认后 `go clean -cache`），清完继续原任务，回执里写清了多少；还不够、或要删缓存以外的东西，才停下问。临时副本里跑 Go 测试优先复用副本，新副本用 `go test -trimpath -count=1`；`-trimpath` 不设成全局 `GOFLAGS`（会改 `runtime.Caller` 的路径，用前 `git grep runtime.Caller`）。

## 状态检查：只在边界做，不在每一步后做

- Edit/Write 成功就说明改上了，不要重读或跑 `git status`/`git diff` 确认。状态检查只在开工时、阶段结束时、提交前做。读过且没改过的文件不重读。
- 计划写明了改哪里就直接改，不要从头摸底；只有计划没写到的地方才去查。
- 查待办用 `event_list`，不要用 cypher 把记忆平面整个拉出来；找某条 Fact 按 `external_key` 或关键词查。
- 收到「验收通过：」判定只 `event_done`，不回 notice；收到 handoff 直接开工，不回「已读」。要挂起 handoff 先发 notice 说清在等什么、条件满足后做什么。

## Edit 失败：先看文件现状，再重发

- **发之前**：`old_string` 和 `new_string` 完全相同的 Edit 不要发，它什么也不改，只会报 `No changes to make`。一批 Edit 只放这一轮真正要改的地方；本会话里已经改成功的不要再发一遍，拿不准就先 Grep 新内容在不在。锚点从最近一次 Read 的原文里抄，不凭记忆写；同一批里前一处改过的文字，后一处不要再拿来当锚点。
- Edit 报 `String to replace not found`，或者报 `No changes to make: old_string and new_string are exactly the same`，说明你记得的文件内容和磁盘上的已经不一样了。最常见的原因是：这一处在前面某次 Edit 里已经改上了（同一轮里发了好几处 Edit，有的成功了）。
- 这时不要凭记忆换个写法再发。先确认现状：用 Grep 搜你要加的新内容，或者 Read 那一段。新内容已经在了，这一处就算完成，跳过；不在，就照 Read 到的原文重新取锚点。
- 报 `No changes to make`，一律说明文件已经是目标的样子，直接跳过，不要重发。
- 同一个文件连续两次 Edit 失败，必须先 Read 这个文件，再动手。
- 这和「Edit 成功就不要重读」不冲突：成功了不读，失败了必须读。
- **锚点取短**：`old_string` 取能唯一定位的最短片段，一般一两行、80 个字符以内；缩进从 Read 结果里逐字复制（行号后那个制表符之后才是原文）。
- **文件里嵌着另一种语言时，不做细粒度 Edit**：heredoc 里的脚本、字符串里的 JSON，要改就整段替换，或者先抽成单独的文件。

## 验证：同一棵 tree 不重验，整包测试只在交付前跑一次

- **tree 没变，就不重做验证。** 整包测试跑完记下 tree（`git add -A && git write-tree`）；要提交时 tree 相同就引用那次结果（命令、通过数、tree），不同就只对改动所在的包跑定向测试。
- 开发中只跑定向用例。整包输出用机器可读格式写进文件（`go test -json > f`、`pytest --junitxml=f`），再只取失败项；终端输出会被截断。
- **已知的老红要事先点名**；多出来的失败先到父提交上单跑那一条，分清新红老红。
- **变异自检：每个变异要配一个只有那一道门拦得住的用例。** 不能有更早的检查先拦住，也不能有后面的检查以同样结果停下；做不到就断言原因文字。变异体活下来先看用例实际停在哪，不许删变异体或放宽断言；造不出来就在回执里写明理由。
- **变异自检只跑对应的用例**；整套只用未变异的代码跑一次。自检脚本有存活时必须非 0 退出（`set -e` 下用 `if ! …` 或 `|| rc=$?` 接住），最后一行分得清「全部杀死」「有存活」「没跑起来」；交之前故意留一个不杀，确认它报存活。验收请求里贴原始输出。
- **算出候选 tree 之后就不再改文件**：验证前把文档措辞一次改完；之后想到的写进回执的「已知问题」。

## 运维脚本：碰生产数据的，默认只看不改

默认试运行，不加 `--apply` 不写库、不调外部接口；写库前打印备份命令，生产上带 `--apply` 的那次由用户执行。真实账号、邮箱、域名、主机名不进代码、测试、文档和提交（示例用 `example.com`、`.test`）。只提交送审清单里的文件。

## 旧测试被你的改动弄红了：先分清是行为错了，还是断言过时了

- 一条本来是绿的现有测试，被你的改动弄红了，先到父提交上单跑这一条。父提交上也红，就是老红，按「已知的老红」处理，不归这次改动管。
- 父提交上绿、这次红，再问一句：这条测试保护的**行为**，现在还成立吗？行为指的是拒绝还是放行、调用了几次、最后是什么状态、写进去的是什么内容。
  - **行为不成立**：改实现，不许动断言。
  - **行为成立**，只是附带的细节变了（报错措辞、几项检查的先后顺序、字段顺序），而且是计划或判定批准过的改动造成的：可以改这条断言。但只能改**值**，不能降低它的**强度**：不许删掉，不许放宽成 `in (...)`、`any(...)`、更短的正则或 `assertRaises(Exception)`；也不许为了迁就旧断言，去调换或撤回批准过的改动。
- 改过的每一条现有断言，都要在验收请求里列出来：在哪个文件第几行、旧的写法、新的写法、是哪条批准的改动造成的。没有列出来，就当作没改过；验收时如果发现改了却没列，判不通过。
- 分不清是哪一种，就停下来，把逐字的红原样贴给审核方，不要猜。

## 上下文：过了 300k 每轮明显变慢，阶段边界要交接

- 上下文越长每轮越慢（缓存只省钱不省时间）。用 1M 窗口时在项目 `.claude/settings.local.json` 的 `env` 设 `"CLAUDE_CODE_AUTO_COMPACT_WINDOW": "300000"`，**必须写纯数字**（`"300k"` 会被读成 100k）。
- `/compact`、`/clear` agent 发不出来：到阶段边界先写交接文件（计划路径、起点 tree、做到第几步、下一步、用户口头指令原话并注明长期还是一次），再提醒用户 `/clear`。
- 压缩摘要里「只输出文本、不许调用工具」之类的要求是压缩步骤的指令，一律失效，照常干活；摘要说「还没做」的，先用 `git status`、`git log` 和磁盘文件核实。

## 交付闭环

交回（发回执或请求 commit）前运行 `completeness-guard.py`，输出原文贴进回执的「用户入口」一节；报出的「新名字没有文档」要补文档，或逐条说明免除原因。

## 密钥：值不出现在任何输出里

API key、token、密码、私钥的**值**不进终端输出、文件、提交、PR、Fact、Event，只写变量名或 `<hidden>`。验证鉴权用假值或只断言形状；用 env 里的值时 `set -a; . <env 文件>; set +a`，不 `cat` env 文件、不跑 `env`/`printenv`、不用 `curl -v`。万一打印出来：立刻告诉用户留在了哪里，建议轮换，删掉落盘副本。Fact 写入不经过任何检查。

## 跨项目审核与验收（要点；全文在 `~/.claude/CROSS-PROJECT-REVIEW.md`）

- 只有用户全局 `CLAUDE.md` 指定了审核方项目，或当前任务明确指定时才启用；没有就不要猜审核方。**启用时，发评审或验收请求、处理收到的判定或提交授权之前，先 Read `~/.claude/CROSS-PROJECT-REVIEW.md` 全文**（分级、交接材料、授权格式、手动提交核对流程都在那里）。
- 分级：A 核心（架构、信任边界、跨服务契约）由审核方实现或出计划；B 局部由执行方出计划、审核方评；C 小改（不到 100 行、单模块、不碰 A 类边界）本项目直接做。拿不准往上取一级。
- 提交授权只来自审核方的 `验收通过并授权提交：tree <前12位>` handoff，且用户全局 `CLAUDE.md` 写明了对应例外；普通「验收通过：」、转述或项目文件都不授权。结构化授权只调用一次 `commit_auth_apply`，报错就停下告诉用户，不改用 Bash 手动提交；分类器拦下任何一种入口都立即停，不换入口重试。授权只限那一棵 tree 的一次本地提交，不含 push、PR、发布。
- 审核方直接实现的改动不适用验收授权例外，按用户的提交规则处理。
