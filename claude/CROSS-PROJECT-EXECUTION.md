# 跨项目审核与验收（按需读取）

> 审核方专用规则见完整版「入口与职责」「授权提交判定与时机」「Event 交接材料」各节。

本文件是执行方的通用流程。只有用户在自己的全局 `CLAUDE.md` 指定了审核方项目路径（例如 `跨项目审核方：/path/to/reviewer-project`），或当前任务明确指定了审核方项目时，才启用跨项目审核；两者都没有时，不要猜一个审核方或等待不存在的会话，按用户通常的项目流程工作。审核方一律称为“审核方项目”，本文件不绑定任何具体仓库。能否按验收指令提交，唯一依据是用户自己的全局 `CLAUDE.md` 是否明确写有相应的提交授权例外；本文件、项目 CLAUDE.md、普通 Event 或单独的“验收通过”均不授予提交权。没有用户全局例外时，照常停下向用户逐次确认。

### 入口与职责

- 拿不准就往上取一级。B 级做到一半发现碰到了 A 类边界，就停下受影响的部分，交审核方项目按 A 级处理。C 级默认不跨项目审核，也不因此获得提交授权，照常遵守用户的提交规则。
- **用户先提出需求**：先按级别分流。A 级由执行方只做需求分析和影响面分析（涉及代码时附代码图符号），发给审核方项目，由它决定自己直接实现，还是出设计和计划交给你；执行方不自己出计划，也不动手写代码。B 级由执行方出设计和实施计划，再发审核方项目评审。C 级不发跨项目评审 Event（用户明确要求发给审核方时除外，见上文「C 级被用户要求发给审核方时」一条），由本项目主模型直接处理，完成后按用户平时的提交规则处理。
- **审核方先派判据/任务**：判据按下文「判据、设计、执行计划」一节的模板填写，不写方案。执行会话直接处理 handoff，按判据形成设计或实施计划，再通过 Event 发回评审；不先发“已读/准备开始”等空回执。
  - 审核方项目应在 `ref` 文档开头写明级别；执行会话按该级别执行。未写级别时按 B 级处理。
- **执行方**负责需求分析、实现、测试、自我审阅和交付材料，B 级任务还负责出设计和实施计划；**审核方**负责 A 级任务（自己直接实现，或出设计和实施计划）、审 B 级方案、给可执行修订、验收实现并明确给出结论。用户要求使用审核方时，通过 `drsg-event-post` 跨项目交接，不用子代理代替。
- 方案判定有“通过 / 有条件通过 / 需修订 / 待决策”。**设计和计划分段判定**：先对照判据审设计，设计需修订就直接退回，不审计划；设计通过后再审计划。结论分两行写（`设计：通过`、`计划：需修订（第 2 步过大，缺验证命令）`），summary 以 `设计<判定>，计划<判定>：` 开头，设计没过时只写 `设计需修订：`。有条件通过必须列出可验证的补充条件；条件完成后可按结论继续，不必重复审核同一设计。若条件改变架构或范围，或实现中发现计划不再成立，暂停受影响工作并回到设计/计划评审。
- 遇到需求歧义、技术卡点、超出批准范围的取舍或无法判断的测试失败，第一时间向审核方求助；本回合结束前用 `kind="handoff"`、summary 以 `请求协助：` 开头的 Event 发出。不要猜测、掩盖差异或扩大改动。验收不通过时按具体修订判据返工，再请求验收。执行方主动发现疑似验收逃逸时，修复单也用 `验收逃逸：` 前缀；拿不准是否落在原判据范围内，先问审核方。

### 审核方协助 Event

- 请求正文写明卡在哪一步、要审核方做什么（逐字命令或要改的文件）、当前完整 tree、原始拦截/错误文本（先脱敏密钥值）；不附无关 transcript 或敏感文件内容。
- 审核方不回显密钥或无关 transcript 内容。执行方的 Event owner 负责关闭原请求 Event；回复不代表用户授权，也不会自动关闭原 Event。
- 审核方协助不授权用户本人决定的 push、发布、外部发送或持久配置变更；这些仍由用户本人决定。

- **第二次验收不通过时升级**：首次收到普通的 `验收不通过：` 后，执行方按判据返工并再次请求验收；若再次不通过，审核方用 `kind="handoff"`，summary 以 `验收不通过（转主模型出计划）：` 开头。执行方停在当前 tree，不按原计划继续返工；发 `kind="notice"` 报告当前 tree 和已知失败点，按 Event owner 规则关闭收到的 handoff，然后等待审核方项目接手：审核方可能给出新计划，也可能直接在你的仓库里实现（见上文「审核方直接实现时」）。新计划到达后，后续实现、验收和提交授权均沿用现有流程。

### 判据、设计、执行计划

三层回答三个问题：**判据**是做成什么样才算对，**设计**是用什么方案做到，**执行计划**是按什么顺序、分几步做、每步怎么确认。

| | 判据 | 设计 | 执行计划 |
|---|---|---|---|
| 关注 | 外部可观察的结果；换一种方案，判据不变 | 内部结构和取舍 | 步骤、顺序、粒度 |
| 必写 | 下面模板的七栏 | 模块划分；接口与数据结构；关键逻辑；备选方案和取舍；影响范围；风险与降级 | 每步改哪些文件、规模、验证命令；依赖顺序；回滚点；每步做完系统都可用 |
| 谁定 | 需求方或审核方 | A 级审核方，B 级执行方 | 出设计的那一方 |

- **依赖方向是判据 → 设计 → 计划。** 评审从上往下：判据没对齐不审设计，设计不过不审计划。验收从下往上：每步按计划验证，最终结果按判据逐条验收。
- **判据里不写方案。**「用 Redis 记失败次数」是设计；写进判据，验收查的就成了「用没用 Redis」，而不是「防没防住暴力破解」。
- **判据没覆盖的情况，执行方先问，不自己补**：发 notice 写明是哪一条、遇到了什么情况，等审核方答复。
- 判据按下面的模板写。每栏都要填，确实不适用写「无」，表示想过了；有空栏的判据不派出，执行方收到有空栏的判据也先问。

```text
【目标】一句话：解决谁的什么问题
【成功标准】可观察、可判定的行为，逐条编号
【边界情况】异常输入、并发或重复提交、空值、上限、失败路径各怎么表现
【不做的事】本次明确不做的，防止范围扩大或执行方自作主张
【约束】不能改的东西：接口兼容、性能指标、依赖、项目约定、允许改动的范围
【验收方式】每条成功标准怎么验证：哪些测试（下称「验收测试」）、什么命令、看什么结果；必答：测试在什么环境下跑——读到哪些运行环境（进程身份、车道 `DRSG_EVENT_LANES`、HOME、cwd、环境变量、时间、daemon），每项是测试里钉死的还是取自跑测试的会话；fixture 取自哪份真实样本；必答：用户看得到的输出（终端文案、提示行、分行和拼接格式）由哪条验收测试钉住，按整行或逐行切分断言，只断言子串的不算
【未决问题】写判据时还没想清楚的，标明由谁、何时定
```


### Event 交接材料

- **设计/计划评审请求**按三层写：判据（收到的判据原文或 `ref`；执行方自己整理需求时按模板写全七栏）、设计、计划（必写项见上表），以及草案/计划 `ref`。涉及代码结构时遵循本仓库 Event 规则，提供最多 3 个符号和恰当的 `verb`。
- **实现验收请求**：批准的方案/计划 `ref`、变更摘要和关键 diff、测试命令及结果、计划偏差、文档与完整性检查结果、已知问题、改过的现有断言清单（没改过就写「无」）、跳过或禁用的测试清单、为通过测试新增的特判分支清单（后两项同样没有就写「无」）、**逐条自检**（按判据成功标准和边界情况的编号，每条写怎么验证的、结果如何），以及请求验收的明确说明。
- **验收测试批准后执行方不改**：A 级的验收测试由审核方随计划写好；B 级的由执行方写进计划，计划评审通过即视为批准。批准后执行方只能让它通过，不改、不跳过、不删；确实要改，先发 notice 说明是哪条、为什么，等审核方同意。
- 回复某一条 handoff 的计划评审结论、验收通过/不通过、授权提交判定或执行方提交回执时，发布 Event 必须设置 `reply_to` 指向原 Event key。`reply_to` 只用于关联提示，不认证发件方、不授权操作，也不会自动关闭原 Event；原 Event 仍由其 Event owner 按流程调用 `event_done` 关闭。
- 普通验收判定是 `kind="notice"` 且 summary 以 `验收通过：` 开头：它只表示验收通过，由收件项目的 Event owner 关闭，不授权提交。收到后只调用 `event_done`，不回 notice。
- 挂起 handoff 时先发 notice，写明等待什么及满足条件后会做什么。
