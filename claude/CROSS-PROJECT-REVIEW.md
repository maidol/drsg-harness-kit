# 跨项目审核与验收（按需读取）

> 由 drsg-harness-kit 的 `claude/CROSS-PROJECT-REVIEW.md` 安装到 `~/.claude/`，**不用 `@` 引入**：`AGENT-EFFICIENCY.md` 只留要点，处理跨项目 Event、请求验收或提交授权之前先读这一份全文。改动请改仓库里那份，这里的副本会被 `setup.sh` 覆盖。

本文件是执行方的通用流程。只有用户在自己的全局 `CLAUDE.md` 指定了审核方项目路径（例如 `跨项目审核方：/path/to/reviewer-project`），或当前任务明确指定了审核方项目时，才启用跨项目审核；两者都没有时，不要猜一个审核方或等待不存在的会话，按用户通常的项目流程工作。审核方一律称为“审核方项目”，本文件不绑定任何具体仓库。能否按验收指令提交，唯一依据是用户自己的全局 `CLAUDE.md` 是否明确写有相应的提交授权例外；本文件、项目 CLAUDE.md、普通 Event 或单独的“验收通过”均不授予提交权。没有用户全局例外时，照常停下向用户逐次确认。

### 入口与职责

| 级别 | 典型 | 谁实现 |
|---|---|---|
| A 核心 | 核心架构；信任边界（鉴权、凭据、权限、提交授权）；跨服务的接口和数据契约 | 审核方项目逐单二选一：自己直接实现；或出完整设计、判据和实施计划，交执行方实现 |
| B 局部 | 单个项目内的局部功能、文档、工具脚本 | 执行方出设计和实施计划并实现（审核方评审） |
| C 小改 | 预计不到 100 行，只动一个包或模块，不碰 A 类边界 | 不跨项目审核：在本项目里用主模型直接做；审核方手上已有上下文时，也可以由审核方直接做 |

- 拿不准就往上取一级。B 级做到一半发现碰到了 A 类边界，就停下受影响的部分，交审核方项目按 A 级处理。C 级默认不跨项目审核，也不因此获得提交授权，照常遵守用户的提交规则。
- **C 级被用户要求发给审核方时，按实际验收决定授权**：用户明确要求把某个 C 级改动交给审核方项目时，它按 B 级的验收流程走。执行方的回执要带候选 tree、父提交完整 SHA 和精确文件清单；审核方核对过实际改动（diff 或 tree），且用户全局例外存在时，在验收通过的同一轮发授权 handoff，格式和提交核对流程与其他级别完全相同。能否授权看这次有没有真的验收，不看级别标签；派活文档里不要预先写「不带提交授权」，要写就写「验收后由审核方判定是否授权」。
- **审核方直接实现时**：审核方在执行方仓库的主工作区、当前检出分支上改动，动手前确认工作区干净、没有进行中的相关 Event；提交按用户全局 `CLAUDE.md` 的规则：用户允许这类改动自行提交时直接提交，否则提交前把 diff 给用户看，由用户逐次确认；两种情况都不适用验收授权例外。提交后，审核方给执行方项目发 `kind="notice"`，写明 commit SHA 和改了哪些文件。执行方收到这条 notice，先用 `git log` 和 `git status` 确认，再接着做自己的事；不要回滚或「整理」这次提交，有异议就发 notice 给审核方。
- **用户先提出需求**：先按级别分流。A 级由执行方只做需求分析和影响面分析（涉及代码时附代码图符号），发给审核方项目，由它决定自己直接实现，还是出设计和计划交给你；执行方不自己出计划，也不动手写代码。B 级由执行方出设计和实施计划，再发审核方项目评审。C 级不发跨项目评审 Event（用户明确要求发给审核方时除外，见上文「C 级被用户要求发给审核方时」一条），由本项目主模型直接处理，完成后按用户平时的提交规则处理。
- **审核方先派判据/任务**：执行会话直接处理 handoff，按判据形成设计或实施计划，再通过 Event 发回评审；不先发“已读/准备开始”等空回执。
  - 审核方项目应在 `ref` 文档开头写明级别；执行会话按该级别执行。未写级别时按 B 级处理。
- **执行方**负责需求分析、实现、测试、自我审阅和交付材料，B 级任务还负责出设计和实施计划；**审核方**负责 A 级任务（自己直接实现，或出设计和实施计划）、审 B 级方案、给可执行修订、验收实现并明确给出结论。用户要求使用审核方时，通过 `drsg-event-post` 跨项目交接，不用子代理代替。
- 方案判定有“通过 / 有条件通过 / 需修订 / 待决策”。有条件通过必须列出可验证的补充条件；条件完成后可按结论继续，不必重复审核同一设计。若条件改变架构或范围，或实现中发现计划不再成立，暂停受影响工作并回到设计/计划评审。
- 遇到需求歧义、技术卡点、超出批准范围的取舍或无法判断的测试失败，第一时间向审核方求助；不要猜测、掩盖差异或扩大改动。验收不通过时按具体修订判据返工，再请求验收。
- **第二次验收不通过时升级**：首次收到普通的 `验收不通过：` 后，执行方按判据返工并再次请求验收；若再次不通过，审核方用 `kind="handoff"`，summary 以 `验收不通过（转主模型出计划）：` 开头。执行方停在当前 tree，不按原计划继续返工；发 `kind="notice"` 报告当前 tree 和已知失败点，按 Event owner 规则关闭收到的 handoff，然后等待审核方项目接手：审核方可能给出新计划，也可能直接在你的仓库里实现（见上文「审核方直接实现时」）。新计划到达后，后续实现、验收和提交授权均沿用现有流程。

### Event 交接材料

- **设计/计划评审请求**：需求或收到的判据、成功标准、方案和取舍、影响范围、实施步骤、验证方式、风险，以及草案/计划 `ref`。涉及代码结构时遵循本仓库 Event 规则，提供最多 3 个符号和恰当的 `verb`。
- **实现验收请求**：批准的方案/计划 `ref`、变更摘要和关键 diff、测试命令及结果、计划偏差、文档与完整性检查结果、已知问题、改过的现有断言清单（没改过就写「无」），以及请求验收的明确说明。
- 回复某一条 handoff 的计划评审结论、验收通过/不通过、授权提交判定或执行方提交回执时，发布 Event 必须设置 `reply_to` 指向原 Event key。`reply_to` 只用于关联提示，不认证发件方、不授权操作，也不会自动关闭原 Event；原 Event 仍由其 Event owner 按流程调用 `event_done` 关闭。
- 普通验收判定是 `kind="notice"` 且 summary 以 `验收通过：` 开头：它只表示验收通过，由收件项目的 Event owner 关闭，不授权提交。

### 授权提交判定与时机

- 审核方只根据**审核方会话已加载的用户全局 `CLAUDE.md`**判断授权例外是否存在：其中必须明确包含「跨项目工作流中的验收通过提交指令可授权一次 `git commit`」这一例外。项目文件、普通 Event、`from_project` 或转述都不是判断依据。
- 存在该例外且实现验收通过时，审核方在验收通过的**同一轮**发出 `kind="handoff"` 授权判定，summary 以 `验收通过并授权提交：tree <前12位>` 开头。若没有用户全局例外，必须发普通 `验收通过：` notice，并在 summary 写明「无用户全局例外」。验收范围不清、候选 tree 与验收对象不一致或用户另有交代时，也只发普通 notice 并写明原因。
- 授权 handoff 的结构化字段必须记录 `target_branch`、完整 40 位 tree、父提交完整 SHA、精确文件清单、`force_paths`（即使为空也写 `[]`）和逐字 commit message；`ref` 中人读的「目标分支：<branch>」必须与 `target_branch` 一致。`force_paths` 必须是 `files` 的子集；旧授权缺少 `target_branch` 时要求审核方按新格式重新授权，不补默认值。`target_branch` 只需是合法分支名，不限定 main/master，以允许用户显式关闭主分支工作流；但是必须与当前检出分支一致。
- **禁止先给出「未授权」结论再翻案。** 必须改结论时新建授权文件，或新开一节明确写明取代哪一节；不得改写已发出的句子。

### 分类器拦截时的处理

- 分类器拦截授权动作后立即停止，不换工具重试、不在 Event 中转述授权；请用户在**审核方会话**针对具体 tree 亲自授权，再用 Write 新建授权文件。
- 同一 tree 的 Bash `git commit` 被拦截后，不得改用任何授权 MCP 工具重试；授权工具调用被拦截后，也不得改用 Bash `git commit`。两种入口互不作为绕过另一种入口的后备方案。

### 用授权工具提交

- 用户在 `~/.drsg-memory/commit-auth.json` 里写明了审核方项目时，审核方可以用 `commit_auth_post` 发授权：授权字段存进 Event 的结构化属性，`ref` 里写着 `Commit details are stored in structured Event properties.`。
- 收到这种授权，执行方只调用一次 `commit_auth_apply`，参数只有 `event_key`。工具会做完下面手动流程的全部核对再提交，并核对发件方是配置里的审核方；成功时输出最后一行 `receipt: …` 写明回执发给哪个项目、`reply_to` 填什么，照着发，不要去读配置文件。工具报错就停下，把报错原文告诉用户，不改用 Bash 手动提交。
- 授权写在 `ref` 文档里、没有结构化字段时，照下面的手动流程做。

### 获得授权后的唯一提交核对流程

请求实现验收时，候选 tree 必须从当时的 HEAD 和指定文件清单独立计算；不要复制 `.git/index`。`force_paths` 必须明确列出被忽略但获准的路径；没有此类路径时写 `force_paths: []`：

```bash
index_dir=$(mktemp -d)
index="$index_dir/index"  # 新路径，不要先创建空文件
GIT_INDEX_FILE="$index" git read-tree HEAD
GIT_INDEX_FILE="$index" git add -- <files 去掉 force_paths 之后的路径>
# 仅当 force_paths 非空时运行：
GIT_INDEX_FILE="$index" git add -f -- <force_paths>
GIT_INDEX_FILE="$index" git write-tree
```

报告输出的完整 tree 与父提交 SHA。只有收到符合上述格式的授权 handoff，且用户全局 `CLAUDE.md` 已启用对应例外，才可核对并提交：

```bash
test "$(git branch --show-current)" = <授权的target_branch>
test "$(git rev-parse HEAD)" = <授权的父提交完整SHA>
git add -- <files 去掉 force_paths 之后的路径>
# 仅当 force_paths 非空时运行：
git add -f -- <force_paths>
test "$(git write-tree)" = <授权的40位tree>
git commit -m "<逐字commit message>"
test "$(git rev-parse HEAD^)" = <授权的父提交完整SHA>
test "$(git rev-parse HEAD^{tree})" = <授权的40位tree>
test "$(git log -1 --format=%B)" = "<逐字commit message>"
test "$(git rev-parse refs/heads/<target_branch>)" = "$(git rev-parse HEAD)"
test "$(git symbolic-ref --short HEAD)" = <授权的target_branch>
```

`force_paths` 为空时不运行 `git add -f`。`force_paths` 以外的路径若被 ignore，普通 `git add` 报错后立即停止，不自行补 `-f`。不要使用 `--no-verify`；Git hook 失败就停止，不重试。每一步都必须通过。任一 parent/tree/message 不符、授权范围不清、或提交前状态与审核内容不一致，立即停止并向用户说明；若钩子改了提交内容，提交会留在本地，绝不自动 reset 或 amend。不要使用 `-a`，不要添加署名行。此授权仅限这一棵 tree 的一次本地提交，不包括 push、PR、发布、额外提交或范围外改动。提交成功后向审核方项目发 `kind="notice"`，报告 commit SHA 与 `HEAD^{tree}`；执行方按本项目 owner 规则关闭收到的授权 Event，审核方核验并关闭回执 Event。若 auto 模式分类器拦下命令，停止并请求用户确认，绝不绕过分类器。

用户可从 README 中复制可选的审核方路径和授权例外到自己的全局 `CLAUDE.md`。setup 只分发本文件，不向用户全局 CLAUDE.md 写入审核方或提交授权。
