# Operating the code graph

This skill is about **keeping the graph alive and honest**: the daemon, the
plugin-fed plane, the rules block, the session guard, and the usage audit.

**It is not the rules for asking the graph questions.** Those live in the
repository's `CLAUDE.md`, unconditionally, because a question about call
relationships rarely announces itself as one — by the time you would think to
load a skill, you have already answered from impression. Do not treat having
read this file as having read those rules, and do not restate them from here.
The full prose is in `docs/{en,zh}/src/coding-agent-codegraph.md`.

## Start with `doctor`

Almost every symptom below is diagnosed by one command, so run it before
forming a theory:

```bash
~/.drsg-memory/tools/codegraph.sh doctor --dir <repo>
```

It checks five things against the running daemon and exits non-zero on the
first that is wrong, so it also works as a gate in a loop over repositories:

| Line | What a failure means |
|---|---|
| `daemon` | nothing holds the database LOCK, or it answers on a different address than `.mcp.json` advertises |
| `plane` / `synced` | the plane is missing, or folded to some commit other than `HEAD` — a commit has not been ingested |
| `root` | the plane was parsed from a different working tree than this one |
| `CLAUDE.md` | no code-graph section at all, or one that names the wrong plane or address, or hard-codes counts that have since moved, or was generated by an older version of the rules |
| `guard` | the `SessionStart` hook is missing, registered twice, or points at a path that no longer exists |

Each of those lines is a failure that happened at least once. The one worth
naming: a plane synced to a *different repository's* tree answers every query
confidently and wrongly.

## The daemon

One per repository. `codegraph.sh {start|stop|restart|status|logs} --dir <repo>`.

Two things routinely trip people up:

- **The address and token come from that repository's `.mcp.json`.** Never mint
  a fresh token to "fix" a connection — that invalidates every client config
  `drsg init` wrote, and the failure moves rather than clears.
- **Identity is the database LOCK file, not the command line.** A daemon
  started by `drsg init` shows `--dir .` in `ps`, so matching on the repo path
  finds nothing and you conclude it is down when it is running.

A repository that does not build `drsg` itself has no binary to launch, so
`restart` there will stop the daemon and fail to start it. The script
remembers which `drsg` was used last; the first start for such a repo has to
name one explicitly.

## Onboarding a repository

```bash
~/.drsg-memory/tools/codegraph.sh install --dir <repo>
```

One command does the whole thing: `drsg init` if the repo has never been
digested, start the daemon, generate the rules block into its `CLAUDE.md`, and
register the `SessionStart` guard.

The block is **generated, not copied**. Copying is the failure this guards
against: the second repository to get a graph inherited the first one's block
verbatim — plane name, port, node counts — and every call made against that
name failed with `not found: plane`. Numbers read out of the live daemon
cannot disagree with it; numbers a human maintains go stale.

If `CLAUDE.md` already documents `drsg-watch` by hand, `rules` reports that and
**leaves it alone** rather than appending a second, contradicting section.
Hand-written sections are the author's; keeping them in step is manual, and
that is a known gap.

## The rules block and its stamp

`codegraph.sh rules --dir <repo>` regenerates the block between the
`<!-- drsg-codegraph:begin -->` sentinels. It is generated **once and never
refreshed automatically** — deliberately, so that no session rewrites
`CLAUDE.md` and invalidates the prompt cache. The cost of that choice is silent
decay, which is what the stamps are for:

- `<!-- rules=<8 hex> -->` — a hash of the generator's own template region,
  placeholders included but never their values. Every repository on the same
  generator therefore shows the same stamp, and it moves only when the prose
  moves. No one has to remember to bump it.
- `<!-- codegraph-cli=<8 hex> -->` in this skill — a hash of `codegraph.sh`'s
  subcommand dispatch. If a subcommand is added, renamed or dropped, prose
  describing the old surface is wrong, and `doctor` says so.

When `doctor` prints `** rules <old>, generator is at <new> — regenerate **`,
re-run `rules` for that repo. When it flags this skill, update `SKILL.md` and
refresh its stamp with the value `codegraph.sh` reports.

## The session guard

`codegraph.sh hook --dir <repo>` registers a `SessionStart` hook (`startup` and
`resume`, roughly 0.4s). It restarts a dead daemon and **says so in the
terminal** — including when the restart fails.

That announcement is the entire point. Without it the MCP tools fail silently,
and a whole session quietly degrades to grep with nobody aware it happened; one
repository's graph ran empty for three days that way. After a successful start
the guard also runs `doctor`, staying quiet unless something is actually wrong.

## Auditing usage

```bash
~/.drsg-memory/tools/codegraph-usage.py [--project X] [--verbose]
```

Counts real calls from the transcripts: the split between hits, empty answers
and mis-addressed calls, plus how often grep was used while the tools were
right there.

Read the output with its limit in mind: **it can show that the graph was
queried; it cannot show that the graph changed the answer.** There is no
suppression arm, so a hit rate is not a usefulness rate. Say that whenever you
quote a number from it.

Two adjustments worth knowing when reading the raw figures: `| grep` pipeline
filters are not graph-avoidance and should not be counted as missed
opportunities, and only symbol-shaped patterns are candidates in the first
place.

## Reaching another repository's graph

A graph is per-repository by construction, so a project that needs to ask about
*other* projects' code — a review workspace, say — has nothing to ask. That is
what `codegraph-router.py` is for: one stdio MCP server, nine `graph_*` tools,
proxying to every registered daemon.

```bash
claude mcp add --scope local codegraph -- \
  python3 ~/.drsg-memory/tools/codegraph-router.py     # run from the project
```

Register the **parked** path, never a path inside a checkout: these scripts are
tracked on a branch, so checking out another one deletes them and the server
fails as a missing file in a session that never mentions the branch.

- **Registry**: `~/.drsg-memory/graphs` (`$DRSG_GRAPHS` overrides), one
  repository path per line, optional TAB + plane when it is not the basename.
  `codegraph.sh install` appends to it. Addresses and tokens are **not** in
  there — the router reads each repo's own `.mcp.json` per call, so there is no
  second copy of a token to rot or leak.
- **Down daemons are normal.** The `SessionStart` guard only fires inside that
  repository, so a graph queried from elsewhere is usually down; the router
  starts it on first use (~1s) and retries. If the start fails it says so, in
  those words, and never returns an empty result — the whole point.
- `graph_repos` is the orientation call: who is registered, on which plane and
  address, and what is up right now. It has no side effects and starts nothing.
  `graph_describe_plane` is the second one, for a question about a repository
  rather than a symbol — the verbs all need a symbol name first, and it is also
  the only source of counts, since the cypher subset has no aggregates.

Only projects that need cross-repository reach should register it; a repository
with its own `drsg-watch` already has the full 22-tool surface.

## Where these scripts live

`tools/codegraph.sh` and `tools/codegraph-usage.py` in the repository are
the **source** — they are what ships. `~/.drsg-memory/tools/` holds the copies
that actually **run**, and this skill points at those.

The split is not redundancy. The repo copies are tracked by one branch, so
checking out any other branch deletes them from the working tree, taking the
tooling with them mid-session. Nothing under `~/.drsg-memory/tools/` is tracked
by any branch, which is exactly why it survives.

Edit the repository copy, then refresh the runtime one by rebuilding the
bundle and re-running its installer — the same path used to set a new machine
up, so there is one way to do it rather than two:

```bash
pack.sh                     # writes dist/drsg-harness-kit-<version>.tar.gz
tar xzf dist/drsg-harness-kit-*.tar.gz -C /tmp && /tmp/drsg-harness-kit-*/setup.sh
```

`setup.sh` is idempotent: it overwrites the runtime copies and re-runs the
installers' self-checks, and touches no database.

## Local topology

Ports and plane names are read from each repository's `.mcp.json`; this is a
convenience map, not the source of truth:

| Repository | Plane | Address |
|---|---|---|
| `dr-strange` | `dr-strange` | `127.0.0.1:7701` |
| `<repo-b>` | `<repo-b>` | `127.0.0.1:7702` |

Run `graph_repos` for the list this machine actually has.

The memory layer is a separate concern on `127.0.0.1:7700` with its own
controller (`~/.drsg-memory/tools/serve.sh`) — do not restart it from here.
