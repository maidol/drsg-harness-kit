# Agent 效率复盘

**一句话**：总耗时 ≈ **轮数 × 单轮耗时**。复盘就是分别量这两个乘数，再按原因归类。不要凭印象下结论，结论要来自统计数字。

执行方规则装在 `~/.claude/AGENT-EFFICIENCY.md`，由全局 CLAUDE.md 引入。

## 用法

```bash
python3 ~/.claude/skills/agent-efficiency-retro/retro.py \
  --project='-data-projects-sub2api*' --since=2026-10-05T09:14:00Z [--until=...]
```

- `--project` 要用 `=` 的写法。目录名以 `-` 开头，空格分隔会被当成另一个选项。
- 目录名是项目路径把 `/` 和 `.` 换成 `-`；worktree 会多出 `--claude-worktrees-<名>`。先 `ls ~/.claude/projects | grep <项目>` 确认。
- `--since` 用派活的时间：Event 的 `created_at` 是 Unix 秒，可以直接传。

## 六项输出怎么读

| 节 | 看什么 | 参考线 / 判断 |
|---|---|---|
| 1 工具调用 | 主会话和子代理的总数 | 约 300 行生产代码 + 600 行测试的功能，连同红绿、变异和提交，**一百次左右**就够了 |
| 2 一轮多调用比例 | 一次回复里发起多个调用的占比（**含子代理**，只看主会话会更低） | 越高越好；2026-10-05 sub2api 主会话只有 5% |
| 3 单轮耗时 vs 上下文 | 只取缓存命中 >90%、输出 <200 token 的轮，排除命中率和写长代码的干扰 | 300k 以内约 7–9s，300–400k 约 13s，500k 以上约 21s。**缓存只省钱，不省这部分时间** |
| 4 重复劳动 | 同一文件被读的次数、`git status` / `git diff` 的次数、子代理调度、代码图调用 | 同一文件读到两位数、`git status` 上百次，都说明有问题 |
| 5 等人 | 主会话中超过 2 分钟、且下一条是用户文字消息的空档 | 计入编排成本，例如需要人转告的 Event |
| 6 no such file | 报错次数和对应的命令 | 多数是工作目录不对：命令失败时 `cd` 不会保留 |

## 统计陷阱

- **调用数按 `tool_use` 的 id 去重，回复数按 `message.id` 去重**：同一条消息在 transcript 里会写成好几行。不要 grep 字符串计数。
- 第 3 节是相关性，不是对照实验：上下文大的轮次集中在会话后段，可能正好赶上更难的步骤。回报时要写上这一条。
- 第 5 节的空档阈值是人为设的（2 分钟），只能当量级看。
- rtk 会吞掉长输出。脚本输出很长时，先重定向到文件再看。

## 复盘报告的骨架

1. 一句话结论：慢在轮数还是单轮，各贡献多少。
2. 时间线：派活、交付、判定各节点的时间，标出等人和串行空等的段落。
3. 原因按影响排序，每条附上数字。
4. 改进分成「已落地」和「待做」两类，每条写清作用对象（全局 CLAUDE.md / 项目设置 / 派活方式）。
5. 证据边界：哪些是统计出来的，哪些是推断。
