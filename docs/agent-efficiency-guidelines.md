# Agent 执行效率准则

**一句话**：agent 慢，通常不是活多，而是**每一轮都慢、轮数又多**。
单轮的耗时由上下文大小决定，轮数由「一轮做多少事」和「有没有重复劳动」决定。这份准则对这两个乘数分别下手。

适用于所有项目里的 Claude Code 会话，包括主会话和接收派活的项目。
**执行方规则（第 1–4 节）**的生效版本是 [`claude/AGENT-EFFICIENCY.md`](../claude/AGENT-EFFICIENCY.md)：`setup.sh` 把它装到 `~/.claude/`，全局 CLAUDE.md 用 `@AGENT-EFFICIENCY.md` 引入，每个会话都会加载。
这份文档负责解释每条规则的由来，并补上派活方和度量两部分；第 6 节的统计由 [`skills/agent-efficiency-retro`](../skills/agent-efficiency-retro/SKILL.md) 自动完成。

---

## 0. 先理解代价模型

- **模型每回复一次，就是一次请求**，每次请求都带着整段上下文。一次回复里可以同时发起多个工具调用：串行调 3 个工具是 3 次请求，并行调用是 1 次。
- **缓存命中只省钱，不省时间。** 缓存省掉的是重复部分的预填充计算，但生成每个 token 时都要对整段上下文做一次注意力计算，这部分随上下文长度增长。
- 实测（2026-10-05 sub2api，共 1706 次请求，只统计缓存命中率高于 90%、输出少于 200 token 的请求）：

  | 上下文 | <50k | 50–100k | 100–200k | 200–300k | 300–400k | 400–500k | >500k |
  |---|---|---|---|---|---|---|---|
  | 单轮中位耗时 | 6.7s | 7.9s | 7.4s | 8.9s | **12.9s** | **17.6s** | **21.0s** |

  **300k 是拐点**：在它以内耗时基本持平，超过后明显变慢。

总耗时 ≈ **轮数 × 单轮耗时**。下面的规则，要么减少轮数，要么缩短单轮耗时。

## 1. 执行方：控制上下文（降低单轮耗时）

| 规则 | 理由 |
|---|---|
| **1.1 自动压缩阈值设为 300k**：在项目的 `.claude/settings.local.json` 的 `env` 里加 `"CLAUDE_CODE_AUTO_COMPACT_WINDOW": "300000"`（**纯数字**：环境变量按 `parseInt` 解析，`"300k"` 会被读成 300、抬到下限 100k，变成每约 67k 压缩一次） | 1M 窗口的模型默认要接近 1M 才会压缩。sub2api 这次整个会话一直在 375k–615k 之间运行，从未压缩 |
| **1.2 每个阶段开一次新会话**：写计划、实现、做下一个功能，阶段之间 `/clear` 或 `/compact` | 这两个命令 agent 自己发不出来，所以 agent 要在阶段边界**写好交接文件，然后提醒用户执行** |
| **1.3 交接文件写五项**：计划路径、起点 tree、做到第几步、下一步做什么、**用户中途口头给的指令**（照抄原话，并注明是长期有效还是一次性的） | 压缩后，写在文件里的东西不受影响，对话里的精确细节会丢，**最容易丢的是口头指令**。丢了的后果有三种：该做的不做、已经授权的事又停下来问、把一次性授权当成长期有效 |

## 2. 执行方：减少轮数

| 规则 | 理由 |
|---|---|
| **2.1 互相独立的工具调用，在同一轮里一起发**。例如开工前要读的几个文件、要查的几个符号、只读的 git 检查、互不依赖的验证命令 | sub2api 901 次回复中，只有 5% 一次发起了多个调用 |
| **2.2 必须分开的才分开**：下一步要看上一步的输出才能决定，或者写操作之间有先后顺序 | 并行不能以牺牲正确性为代价 |
| **2.3 自检**：如果连续三轮都只读了一个文件、或只跑了一条只读命令，就停下来想想能不能一次读完 | 给模型一个能观察到的触发条件，比「尽量并行」这种笼统要求管用 |

## 3. 执行方：不做重复劳动

| 规则 | 理由 |
|---|---|
| **3.1 默认不用子代理**；计划已经评审通过、改动在几十个文件以内的，用 `executing-plans` 在主会话里直接做 | 功能 1 派了 27 个子代理，每个都从零开始读代码：同一个 `AccountsView.vue` 读了 59 次，调度还额外花了约 220 次调用。功能 2 禁用子代理后，子代理调用是 0 |
| **3.2 状态检查只在三个时点做**：开工时、一个阶段结束时、提交前。Edit / Write 成功就代表已经改上了 | 功能 1 里 `git status` 跑了 202 次，`git diff` 跑了 140 多次 |
| **3.3 读过、自己又没改过的文件，不要重读**；要看改动后的样子，只读改动的那一段 | 同上 |
| **3.4 计划已经写明改哪里的，就直接照计划改**，只对计划没写到的地方做探索 | 功能 1 调了 463 次代码图，计划里早已写明了函数和字段 |
| **3.5 tree 没变，就不重做验证**：整包测试跑完记下 `git write-tree`；要提交时 tree 不变就直接引用那次结果，变了只跑改动所在包的定向测试 | 功能 2 用户说「创建这个 commit」后 53 分钟才提交：同一棵已全量验证过的树，又跑了 3 次整包、手工重做了一遍变异，最后是用户叫停的 |
| **3.6 整包测试只在交付前跑一次**，输出用机器可读格式写进文件（`go test -json > 文件`），只取失败项；有过滤代理的，用直通方式（`rtk proxy`）；已知老红事先点名 | 功能 2 段整包跑了 7 次、约 25 分钟（一次约 3.6 分钟）；每次输出超过 10 MiB，被 rtk 截断，模型只能读日志副本重新解析或再跑一遍；每次退出码 1 都来自同样 3 条老红 |

> 正常的量级：一个约 300 行生产代码加 600 行测试的功能，含实跑红绿、变异自检和提交，**一百次左右的工具调用**就够了。功能 1 实际用了约 1500 次。

## 4. 执行方：Bash 工作目录

| 规则 | 理由 |
|---|---|
| **4.1 每条命令都自带目录**：`go -C backend …`、`git -C <目录> …`、`(cd backend && …)`，或者用绝对路径 | **命令成功时 `cd` 会保留，失败时不会**（已实验验证）。TDD 的红阶段测试本来就要失败，所以最容易踩到 |
| **4.2 遇到 `no such file or directory`，先跑 `pwd`**，不要猜 `../` 前缀 | sub2api 这次报了 23 次这个错，其中 19 次是工作目录不对，而且两个方向都猜错过，前后浪费了 29 轮 |

## 5. 派活方：拆活与编排

| 规则 | 理由 |
|---|---|
| **5.1 两个功能如果只在接口或测试桩上冲突，就允许并行**：分别放在两个 worktree 里做，合并时再解决冲突；验收时分别核对各自的起止 tree | 我当时要求「功能 2 从功能 1 的终点开工」，结果功能 2 的计划通过后空等了 3 小时 42 分钟 |
| **5.2 只在真正有依赖时才串行**：例如后一个功能要调用前一个功能新加的接口，或者两者改的是同一段逻辑 | 串行是为了正确性，不是为了验收时比对方便 |
| **5.3 接收方要能自己发现待办**：两边都开定时检查（例如每 20 分钟调用一次 `event_list`），完成条件写进定时任务里 | 这次三轮评审，每轮都靠用户转告「收到评审了，执行」 |
| **5.4 评审的轮数要算进成本**：让对方出计划、我来评审，是在「对方更熟悉代码」和「多来回几轮」之间的取舍。这次三轮评审用了 77 分钟。小改动可以考虑由我直接给出计划 | 采用哪种方式由用户决定（见「我设计，别的项目实现」） |

## 6. 度量与复盘

做完一个功能、或者用户觉得慢时，从 `~/.claude/projects/<项目>/*.jsonl` 里统计下面几项。**用统计结论说话，不要凭印象**：

| 指标 | 怎么算 | 参考线 |
|---|---|---|
| 工具调用总数（含子代理） | 统计 `tool_use` 数，按 id 去重 | 同等规模的功能约一百次 |
| 单轮耗时与上下文的关系 | 工具结果到下一条 assistant 消息的时间间隔，按 prompt 大小分档 | 300k 以上明显变慢 |
| 一轮多调用的比例 | 一条 assistant 消息里含多个 `tool_use` 的占比 | 越高越好；这次是 5% |
| 重复读取 | 同一个文件被 Read 或 `sed -n` 的次数 | 一个文件读到两位数，说明有问题 |
| 等人时间 | 超过 2 分钟、并且下一条是用户消息的空档 | 计入编排成本 |
| 报错浪费 | 报错那一轮，加上紧随其后的排查轮次 | 按原因分类 |

统计时注意两点：数调用要按 `tool_use` 去重，不要 grep 字符串；同一条消息在 transcript 里会写好几行，要按 `message.id` 去重。
