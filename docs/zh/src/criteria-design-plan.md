# 判据、设计、执行计划

规则正文在 [`claude/CROSS-PROJECT-REVIEW.md`](https://github.com/maidol/drsg-harness-kit/blob/main/claude/CROSS-PROJECT-REVIEW.md) 的「判据、设计、执行计划」一节；这里只放说明和一个完整的例子。

## 三层各回答什么

- **判据**：做成什么样才算对？只写外部可观察的行为，换一种方案判据不变。
- **设计**：用什么方案做到？模块、接口、关键逻辑、取舍、影响范围、降级。
- **执行计划**：按什么顺序、分几步做，每步怎么确认？

评审从上往下，判据没对齐不审设计，设计不过不审计划；验收从下往上，每步按计划验证，最终按判据逐条验收。

## 例子：给登录接口加防暴力破解

### 判据（按七栏模板，不提实现）

```text
【目标】防止对登录接口的密码暴力破解，同时不影响正常用户
【成功标准】
  1. 同一账号连续 5 次密码错误，锁定 15 分钟，返回错误码 ACCOUNT_LOCKED
  2. 同一 IP 每分钟超过 20 次登录尝试，返回 429
  3. 输错 1 到 4 次后输对，正常登录，并清零计数
【边界情况】
  - 锁定期间输入正确密码：仍然拒绝
  - 锁定到期：自动解除，不需要人工干预
  - 账号不存在：同样计数，返回和密码错误相同的提示，避免账号枚举
【不做的事】验证码、短信或邮件通知、管理后台的解锁按钮
【约束】登录接口的请求和响应格式不变；P99 延迟增加不超过 10ms
【验收方式】自动化测试覆盖成功标准 1–3 和全部边界情况，审核方在同一棵 tree 上重跑
【未决问题】阈值是否做成可配置：产品下周给结论，本期先写在配置项默认值里
```

「账号不存在」这一条，写判据的人知道怎么处理，但容易觉得太显然而不写；较弱的执行方多半想不到账号枚举。模板的作用就是逼着把这类内容写下来。

### 设计（选定方案并说明理由）

- 计数放在 Redis：需要过期能力，也要扛住高频写。
- 键为 `login_fail:{account}` 和 `login_rate:{ip}`，用 TTL 实现自动解锁。
- 在认证中间件里拦截，不改业务层。
- 取舍：Redis 不可用时放行，不拒绝。
- 影响范围：认证中间件和配置项，不碰用户表。

如果把「用 Redis 记失败次数」写进判据，验收查的就成了「用没用 Redis」，而不是「防没防住暴力破解」。

### 执行计划（逐步落地）

1. 配置项和 Redis 计数工具函数，附单元测试，约 80 行。
2. 中间件接入账号锁定逻辑，附集成测试（覆盖 5 次锁定和到期解锁），约 120 行。
3. IP 限流，附测试，约 60 行。
4. Redis 故障降级，附故障注入测试，约 50 行。

每一步都能单独提交、单独验证，做完任何一步系统都可用。

### 分段评审的结论

```text
设计：通过
计划：需修订（第 2 步缺验证命令）
```

Event 的 summary 写成 `设计通过，计划需修订：…`；设计没过时只写 `设计需修订：…`，不审计划。

### 验收不通过时

结论引用条目编号，summary 带原因类别：

```text
验收不通过：[漏测边界] 2 不通过：超限返回了 500 而不是 429
```

类别只用七种：判据缺失、理解偏差、方案不成立、漏测边界、范围偏移、钻判据空子、约定不符。复盘时运行 `agent-efficiency-retro`，它的第 7 节按这些类别统计首次验收通过率和原因分布。
